# 编排框架（team）：脚本 + fresh 子代理

> 本文件是运行架构的**唯一说明**。阈值在 `scripts/config.py` 的 `TEAM` / `SCORE` / `GRID` 三段；
> 细则以本文件为准，脚本以 `team.py` / `score.py` / `billing.py` / `grid.py` 为准。
> 单一出处：角色与团队机制=本文件；决策日顺序=`SKILL.md` §8.1.1；阈值数值=`scripts/config.py`；公式与历史证据=`references/engine-notes.md`；规则映射=`references/logic-map.md`；数据源=`references/data-sources.md`；入口运维=`README.md`。
> 适用本金：**本部署 5 万单账本**。

---

## 0. 第一原则

**凡是要重复执行的动作 → 规则引擎代码；凡只需判断一次的动作 → 才交给 LLM。**

这条不是风格偏好，是成本算术逼出来的：

| 做法 | 单位成本 | 可复现 | 可回测 |
|---|---|---|---|
| 规则引擎（Python） | ≈0（本地算力） | 是，同数据同结论 | 是 |
| LLM 读一个文件做个判断 | 0.5–2 元 | 否，同一输入两次可能不同 | 否（生成内容无 PIT） |

所以：筛选、打分、仓位、网格、记账、体检 → **全部代码**；
只有「这只票有没有雷」「这期赚在哪、下期盯什么」→ **才用 LLM**。

另一个反直觉推论：**省 50 元 token 相当于权益层多赚 0.58%**（5 万本金、权益层 8,600 元）。
在 5 万这个量级，优化 token 成本比优化选股容易得多。

**决策日的执行顺序与各步职责，唯一权威见 `SKILL.md` §8.1.1，本文件不复述顺序、也不维护第二份清单。**

### 2.1 怎么真跑起来（team.py 的机制）

`team.py --run` 只跑代码步骤并**生成任务书**；LLM 步骤必须由 Lead 真起执行者（本部署为 fresh 子代理）。

> **执行顺序不在这里重复**：决策日的 10 步唯一权威清单见 `SKILL.md` §8.1.1（顺序错了研究结论会影响不到当期计划）。
> 本节只讲 team.py 自己的机制：`--run` 生成任务书、`--stage` 打印任务书、`--ingest` 验收并推进。

- `--stage Tn` 只出任务书（写进 `out/agent_tasks/`，正文由 Lead 原样转交队友/子代理）；
- `--ingest Tn` 校验产物（文件/表头/枚举/目录齐全性）→ 标 ok → 自动推进下一步；
  没通过就重做那一步，**不许跳过验收往下走**；
- `--ingest T4` 会用 `resume=True` 续跑引擎（保留已完成的 T2/T3 状态，不冲回 pending）。

**失败降级**（不许整条链崩）：
- T0 不新鲜 → 直接退出，不产生计划；
- T3 深取不齐 → `--ingest T3` 直接拦下并列缺哪几只，不进 T4；
- T2/T4 的 CSV 缺文件/空表/缺列/`need_deep` 写成 true/false（旧契约）→ `--ingest` 全部拦下并说明怎么改；
- T8 没有任务窗口（周期结算模式）→ **不在此分段结算**，成本留到下一次决策第 2 步；记分卡如实写「本次窗口未结算」，绝不自己估数字；
- T10 失败 → 不影响当期决策，只少一份复盘。

## 4. 评分与奖励（`score.py`）

### 4.1 口径（写死）

```
净收益率 = 组合收益率 − token 成本率          ← 评分用这个
奖励     = 净利润 × 档位比例                  ← 从本金划出，全部转次年 token 预算
实际留存 = 净利润 − 奖励                      ← 继续留在组合里复利
```

- 赚到的钱**继续投资**，本金变大 → 下期基数变大；
- 奖励**从本金里划掉**给 AI，**不是交易成本**；
- 奖励**全部**转为次年 token 预算额度（`reward_split_to_budget = 1.0`）：对 AI 而言奖励就是 token；额度是上限，实际成本率取决于真实花费，评分只按真实花费扣。

### 4.2 评级

| 评级 | 净收益率（扣 token 后） | 奖励比例 |
|---|---|---|
| A | ≥ 4.5% | 10% |
| B+ | ≥ 3.0% | 7% |
| B | ≥ 2.0% | 5% |
| B- | ≥ 1.3%（银行定存线） | 5% |
| C | ≥ 0 | 0 |
| D | < 0 | 0（亏损无奖励） |

### 4.3 两条护栏

1. **风险否决**：净收益达到 A 级但期间最大回撤深于 **20%** → 降到 B+、奖励减半。防「赌一把拿 A」。
2. **分布大于单次**：单次评分是运气。12 期目标分布 `D=0, C≤1, B≥6, B+≥3, A≥1`（期望净收益 2.6%–3.0%）。
   A 级是**行情给的**，不是能设计出来的；把 A 当 KPI 会逼出赌徒行为。

### 4.4 全转预算的算术（为什么现在全转）

设 A 级（净收益 4.5%）、奖励 10%、100% 转预算：
5 万本金 → 净利润 2,250 元 → 全部转次年预算 225 元 → 次年预算 375 元 = **0.75% 的额度**。
但额度只是上限：实际成本率 = 真实花费 ÷ 本金，评分按真实花费扣，不花就不扣。
奖励越多、预算越大，是用去年的业绩换明年的额度，不是自动扣费。

### 4.5 年度结算（每年 1 月 1 日，`monthly.py --annual`）

- 平时月报只统计、不评分、不结算；**年报是唯一的结算日**。
- **档位按等价年化净收益率**定（不足一年也按 `(1+净收益率)^(365/天数)−1` 折算，天数 = 年内首个到最后一个净值日）；**奖励 = 当年净利润 × 档位比例**（不按年化理论值发钱；当年净利润 = 当年毛利 − 当年 token 实花）。
- 结算：奖励（评估期后>0）**从账户现金划出**转次年 token 预算；**本金重置为「年末净值 − 奖励」**，下一年收益率以剩余净值为起点。
- 总收益按 `meta.cum_index *= (1+当年收益)` 跨年**链式累计**；`meta.annual_baseline` 重设已实现盈利基线，避免同一笔盈利重复放大可投资本；记录写 `meta.annual_settlements.<年>`，结算前备份账本、同年幂等；重渲染年报加 `--no-settle`（不重复结算）。

### 4.6 年报指挥月报（`annual_plan.md`）

月报与年报是**同一个定时任务**（每月 1 日 22:00，1 月 1 日自动切年报模式）。年报写 `out/team/annual_plan.md`（年度目标 / 分季检查点 / 参数冻结清单 / 每月必答 / 给月报的附加任务 / 年度复核触发条件），下一年每月月报**只读**它，并在月报「本年计划对齐」一节逐条回答「每月必答」；冻结参数不得由月报直接改，越界只能写 `pending_changes` + `annual_review_request.md` 请用户拍板。年报另含**选股评分体检**（`score_panel.health`：面板覆盖 / 分维度 IC / 五分组差 / 命中率；不足 26 周或 30 条只写「维持现状」，只记录、不许据此改分值）；周决策每周把候选评分归档到 `out/archive/scoring/`，供年报体检用。

## 5. 计费（`billing.py`）

### 5.1 唯一数据源

DSH 计费插件账本 `<account>/.dshw-usage.json`（路径由 `billing.py` 按当前账号定位，文档不写死绝对路径）：
顶层 `events` 里每条 `{ts(毫秒), day, model, cost, tokens}`，另有 `accounting.books[*].days[*].debitUnits`（1e8 = 1 元）。

**不要**去账号页抄余额，也不要自己按 token 数 × 单价估——单价随模型变，估出来是假数字。

### 5.2 唯一结算口径：**周期结算**（读插件扣费记录）

| 项 | 口径 |
|---|---|
| **主** | 插件账本 `$DSH_HOME/.dshw-usage.json` 的 `events[]` 在「上次结算终点 → 现在」区间的 `cost` 累计（`billing.py --task-end`） |
| 旁证 | `accounting.books[active].days[day].debitUnits / 1e8`（当日全账户实扣），只对账展示，不记账 |

**结算时点 = 下一次决策会话的第 2 步**：上一次决策会话 + 期间巡检（巡检按 0.01 元/天定额记）一次补记；
本次决策自己的花费留到下一次第 2 步（会话没结束时数不准）。终点落盘 `out/team/billing_cycle.json`，绝不重复计数。

**可选窗口**：想单独量某一次任务窗口时，仍可 `--task-begin` 记快照、`--task-end` 结算该窗口（basis=snapshot）；默认不需要开窗。

**为什么能按时间切**：`events[]` 每条只有 `{ts, day, model, cost, tokens}`，**没有 session id**；决策固定周六，因此「上次结束 → 现在」就是这一周期的本机花费（含开发对话，如实计入、不挑拣）。

**三条硬规矩**：
1. **不在任务里自己核算**：不按 token 单价估算、不按余额均分、不编数字；区间内没有记录就记 0 并说明。
2. **账本归属单一**：本部署只有 `50k` 一个账本，任务成本全部计入该账本；将来若加账本，归属口径须先由用户拍板再改 `billing.py`。
3. **不重复计数**：结算后写终点；`team.py --run-t8` 没有窗口时分段结算跳过，成本统一留到下一次决策第 2 步。

### 5.3 产物与账本

- `out/billing.jsonl`：每次结算一行流水（`source=events-cycle` 为周期结算，`snapshot` 为可选窗口）；
- `out/budget.json`：各账本 `base / bonus / carry_over / spent / remaining / runs`；
- `out/team/billing_cycle.json`：上次结算终点（唯一的时间锚）；
- 命令：
  ```bash
  python billing.py --task-end --ledger 50k          # 决策第 2 步：补记上一周期
  python billing.py --flat-yuan 0.01 --ledger 50k    # 巡检：0.01 元/天定额
  python billing.py --status --ledger 50k            # 预算 + 今日实扣 vs 已入账
  python billing.py --settle --day 2026-11-21        # 只读对账（不记账）
  python billing.py --purge-test                     # 清掉自测写进真实账本的假记录
  ```

**自测不要污染真账**：往真实 `out/budget.json` 写测试流水会让预算永久偏小（会留下假流水与假奖励，需用 `--purge-test` 清掉）。要测就得用临时 `A_SHARE_WORKDIR`。

本地跑脚本**不花 token**（只有 LLM 步骤花）。所以决策日一次全流程的成本 ≈ T2/T4/T9 三个 LLM 步；T8 评分移到月报（一周一次 → 一月一次）。

## 6. 低买高卖（网格，`grid.py`）——**已验证，结论：不启用**

### 6.1 设计

- 锚 = 200 日均线；偏离 ±8% 触发；每次调 20% 目标仓位；口径是**权益 sleeve 内部权重**（base 50%，floor 20%，ceiling 80%）；
- 硬约束（成本算术，不是建议）：只在 **ETF** 上做（个股卖出印花 0.05% 吃光价差）、单笔 **≥ 5,000 元**（往返成本率 ≤ 0.20%）、间距 **≥ 5%**、年换手 ≤ 2 次往返；
- 状态：`config.GRID["enabled"] = False`、`verified = False`。**回测没通过之前不进决策链。**

### 6.2 回测结论（4 只 ETF，2012–2026 全周期）

对照组是「同 base_weight 仓位、零交易」的固定持有——**不是满仓买入持有**（拿网格比满仓只会得出「仓位低所以赚得少」这种废话）。

| 指标 | 结果 | 门槛 | 判定 |
|---|---|---|---|
| 平均超额（vs 固定持有） | **−13.82pp** | > +0.5pp | ✗ |
| 最大年换手 | 18.8 笔/年 | ≤ 8 笔/年 | ✗ |
| 回撤差（vs 固定持有） | −3.32pp | ≥ −3pp | ✗ |

参数扫描 8 组（band 8/12/15/20% × step 20/30%）**无一组通过**：
band 20% 时换手 3.8 笔/年达标，但超额恶化到 −16.67pp。

### 6.3 为什么失败（分年度证据）

band 15% / step 20% 的逐年结果：**多数年份小幅跑赢（+0.4 ~ +3.4pp），但在单边大牛市大幅跑输**：

| 年份 | 区间涨跌 | 网格 vs 固定持有 |
|---|---|---|
| 2006（510050） | +115.7% | **−25.5pp** |
| 2007（510050） | +130.5% | **−42.0pp** |
| 2008（510050） | −67.0% | −15.7pp（跌市里卖飞后反弹没吃到） |
| 2014（510300） | +50.9% | −10.0pp |
| 2020（510300） | +27.4% | +0.8pp |
| 2022（510300） | −21.1% | +1.3pp |
| 2024（510300） | +16.5% | +3.4pp |

**结论：网格 = 卖出波动率，收益分布左偏。** 它在震荡市收小钱、在最大的上涨年份缺席，
而「缺席最大上涨年份」的代价远大于震荡市的小幅超额。这与「靠复利赚更多钱」的目标冲突。

### 6.4 还有一条与行情无关的否决理由

5 万本金下，单只 ETF 持仓约 3,150 元，偏离 8% 触发时的目标调整额只有 **≈432 元**，
远低于 **5,000 元**单笔下限 —— **网格在本部署 5 万本金下结构性不可行**。
更直接的原因：432 元的往返成本约 3.4%（两笔 5 元最低佣金），价差 5% 全被佣金吃掉。
实跑 `grid.py --signal` 的输出就是证据。

### 6.5 如果以后还想做

唯一有意义的改造方向：**估值分位网格**（按 PE/PB 历史分位而非价格均线调仓），
它不会因为「涨了」就卖，只在「贵了」时卖。但那需要 PIT 估值序列——本技能目前**没有**，
所以这是「待补数据」之后的事，不是现在能做的。

| 层 | 频率 | 谁 | 内容 |
|---|---|---|---|
| L1 归因 | 每次 | 代码 | 现金 carry / R2 carry / R3 beta / alpha（alpha **不可测**，直接写不可测） |
| L2 记分卡 | 每月（月报） | 代码 | 本期评分 + 12 期分布 vs 目标（决策日不评分，一周看不出能力） |

| L5 参数复核 | 季度 | LLM | 只动**可回测层**（现金容器 / 网格间距 / 再平衡阈值），每次只改 1 个参数，必须有样本外 |
| L6 策略复盘 | 月报 | LLM | 回查策略假设（regime 判定 / 权益预算用满没 / ETF 与场外承接 / 建仓条件单成交失效 / 止损事后对错 / 现金层 / 费用换手 / 各层差异），每条带证据，≤5 条改进项分 A/B 类 |

## 10. 诚实边界

1. **评分不构成收益承诺**。单期评分是运气，看 12 期分布。
2. **token 成本是唯一确定的成本**，收益不确定；本框架不宣称能稳定跑赢银行定存。
3. **alpha 不可测**：个股层没有 PIT 数据，「选股贡献了多少」无法归因，只能说 beta + carry。
4. **网格已验证不通过**，不启用；启用它需要新的、可验证的改造方案（见 §6.5），不是调参。
5. **多 agent 不产生信息**：同一个模型读同一批数据，分歧是噪声。本框架里 agent 唯一不可替代的价值是
   **动机分离**（审计方与实现方不是同一个角色），其次是**并行**（数据深取与文档同步）。别指望角色数量带来 alpha。
6. **研究层已接进引擎**：`plan.py:apply_research()` 在风险闸之后消费
   `out/stage1b_research.csv`——`reject` 剔除、`downgrade` 权重系数 ×0.5，结果写进
   `plan["research_filter"]` 与计划 note。文件缺失/空表一律 fail-open 原样放行（研究层是可选增强）。
   **L1 契约已补齐**：`snapshot.py` 生成 `out/data_snapshot.csv`（300 只个股全池：
   规模/流动性/ROE/现金流/负债/成长/估值/回撤/新鲜度），`run.py` 在 judge 之后自动调用，`--only-plan` 也刷新。
   但 `risk_tag/event_tag` 仍靠 LLM 手搓、不可复现——这一条不变，别把研究层结论当已验证事实。
7. **场外 R2 腿走影子账**：`wealth_positions` 里 `venue=OTC` 的持仓由 `otc_book.py` 记账（T+1 确认净值成交、
   市值按累计净值比、赎回费按持有天数），`paper.settle()` 与 `patrol` 都把它算进总资产，账本风险画像与
   计划的名义 40% 口径一致。仍注明的边界：①场外无 PIT、不回测；②账本与真实 APP 确认差 1–2 个交易日。
8. **定时任务挂在会话上**：`schedule_create` 的提醒属于当前会话，会话一归档/清理就消失
   （提醒会随会话一起丢失）。要么保持会话常驻，要么每次重建后用 `schedule_list` 核对（**技能侧没有可核对的落盘文件**，
   `storages/schedule.json` 是宿主应用的内部状态，不保证可读）。这是环境限制，不是技能能修的。
