# 事件面采集与判读手册

> 谁读：**采集端（脚本）**（跑采集、整理简报）、**Lead**（判读高优先级事件、出 `mult`、决定持仓处置）、改代码的人（权重与阈值的来历）。
> 单一出处：角色分工=`references/team-framework.md`；决策日顺序=`SKILL.md` §8.1.1；事件面规则与校准证据=本文件。
> 口径代码：`scripts/news.py`（`R_EVENT` / `C_EVENT` / `r_score()` / `c_score()` / `tier_of()`）。
> 校准数据：`out/news_calib.csv`（两池 602 条事件）。校准脚本：`scripts/news_calib.py`。
> 最后标定：2026-10-29。**标 [先验] 的权重没跑过数据，不许说成「实测」。**

## 一、谁来做，各自负责什么

一句话：**事件面 = 采集端（脚本） 用代码采集、Lead 判读并给处置档**——把持仓和候选的公告/新闻/异动翻译成「R 分风险 + C 分催化」，交出 `mult`。决策前提是 采集端（脚本） 先**整理本机交易日 19:00 已取数据**（`stock prefetch` 统一取数）（核对 `data_as_of` = 最近交易日、取数成功率、候选/持仓清单）；**决策日不重取行情**，只采周末新增公告/新闻。

**采集端（纯代码，0 判断）**
0. **先整理本机交易日 19:00 已取的行情/财务/估值产物**（`out/stage3_plan.json` 的 `data_as_of`、`stage1_funnel.json` 取数成功率、候选/持仓清单）——数据不是最近交易日就如实报告，决策日不重取；
1. 扫当日持仓股 + 候选股的事件面（公告、新闻、异动、除权）；
2. 由 `news.py` 按规则打 `r_score` / `c_score`、定处置档，写出机读与人读产物；
3. 把 `out/news_events.csv`（机读）和 `out/news_brief.md`（人读）整理成交卷。

**Lead 判读端（每次决策日一次性判断）**
4. 读简报里的高优先级事件，逐条确认：是什么事、影响谁、按哪一档处理、为什么；
5. 按处置档给 `mult`（权重系数），**持仓处置由 Lead 手工出单**（代码不会自动减半）；
6. 高优先级事件逐条写人话，结论放在 `news_brief.md` 顶部。

**都不做的事**
- **不改资格**：能不能买由漏斗与四道闸门决定，事件面只能否决或加减权重；
- **不预判点位**：不给目标价、不猜涨跌幅度；
- **不碰 ETF / 场外基金 / 现金层**：那些没有个股公告事件面，只扫**个股**；
- **不做每日巡检**：巡检是 `patrol.py` 纯代码的活（账本/数据/任务书一致性），与事件面无关；
- **不自己加数据源**：只用 `news.py` 封装的同花顺 iNews + 巨潮公告，不临时换源。

## 二、什么时候跑

| 谁 | 什么时候跑 | 干什么 |
|---|---|---|
| `stock prefetch` + `run.py`（交易日 19:00，Windows 计划任务）与 `patrol.py`（交易日 20:00，DSH 会话） | 每个工作日（周一至周五）19:00 / 20:00 | 19:00 先 `python -m stock prefetch` 统一取当日收盘基础数据，再 `run.py --capital 50000` 只读热缓存出 stage1/2/3；20:00 由 DSH 会话跑 `patrol.py` 查账本/任务书一致性。**不看新闻。** |
| **事件面**：采集端（脚本） 采集 + Lead 判读 | **只在决策日**（每周六 20:00 那一轮，研究层交卷之前完成判读；**不重取行情**，只采周末新增公告/新闻） | 扫持仓+候选的事件面，出 R/C 与处置档 |
| Lead | 决策日当晚 + 次日早间 | 按处置档改权重、安排调仓（规则引擎只算手数与价位；真正的下单/成交走 `paper.py` 或用户手动） |

**为什么不是每天**：新闻的价值衰减极快（≤3 天 15 分、≤30 天 8 分），每日扫一遍却不用，
等于把额度换成噪音。并且**周六没有新行情，但周末新增的公告/新闻是别的时间拿不到的新信息**——这正是事件面必须留在决策日、而行情不必重取的原因。新闻只在决策日扫，不要每天巡检跑；发现要命的事件就在次日上午由 Lead 安排处理。

决策日的时间位置（完整 10 步的顺序唯一权威见 `SKILL.md` §8.1.1；这里只标事件面的位置）：

```
体检 → 漏斗(规则) → 引擎出候选 → 【事件面：采集端（脚本） 扫候选 + 持仓 → Lead 判读出 mult】→ 研究层 → 计划书(Lead) → 次日执行（卖出开盘价 / 买入限价条件单）
```

**位置为什么在这里**：设计是「专门收集**研究层筛选出来的**优质项目的新闻」——
事件面放在「引擎出候选之后、研究层交卷之前」：先有候选名单，只扫这批 + 持仓，不做全市场海选。
`mult` 由 `plan.apply_news()` 在计划书定稿时乘进选股权重，**必须在计划书定稿前交卷**；
交晚了这一轮就退回「不看新闻」，但要如实说明。

## 三、具体怎么干（六步）

### 第 1 步（采集端（脚本））：确认输入齐了
```bash
python scripts/news.py --help
ls out/stage3_plan.json out/stage1_candidates.csv     # 持仓与候选
```
- 持仓来自 `out/stage3_plan.json` 的 `positions`（只取 `layer == "个股"`）；
- 候选来自 `out/stage1_candidates.csv`，按分数取前 `config.NEWS["max_codes"]` 只；
- 两个都没有 → 空跑，写空简报，**不编事件**。

### 第 2 步（采集端（脚本））：跑扫描（纯代码，0 判断）
```bash
python scripts/news.py                # 默认窗口 config.NEWS["days"]
python scripts/news.py --days 7       # 只扫最近 7 天（周末补扫用）
python scripts/news.py --limit 5      # 只扫 5 只（调试用）
python scripts/news.py --offline      # 断网时出空简报，不报错
```
这一步已经做完：抓取 → 噪音过滤 → 硬雷关键词 → 打 R/C → 定档 → 写 csv。
**它给出的分是规则算的，不是人的判断**；人的判断体现在第 3–5 步（Lead）。

### 第 3 步（Lead）：读结果，先看高危
```bash
python scripts/news.py --help >/dev/null
# 读 out/news_brief.md（按 level 排序，高优先级在最前）
```
判读顺序固定：**先看「高」→ 再看「中」→ 最后扫一眼低优先级有没有漏网的硬雷**。

### 第 4 步（Lead）：对每条高优先级事件写一句人话
必须回答三件事：
1. **是什么**（哪家公司、什么事、发生日、来源）；
2. **影响谁**（持仓还是候选；占组合多少）；
3. **按哪一档处理**（否决 / 降权40 / 降权15 / 加分15 / 加分10 / 不干预）+ 为什么。

### 第 5 步（Lead）：结论（写进 `news_brief.md` 顶部）
只写三行：
```
- 否决：000977（立案调查，R=60）→ 持仓处置由 Lead 在决策日手工出单（代码不会自动减半）
- 降权：600519（诉讼仲裁，R=45 → 0.60）
- 加分：000999（回购，C=16 → 1.10）
```
没有就写「今日无需要干预的事件」。**不要罗列全部事件**，那是 csv 的活。

### 第 6 步：交卷 + 自检（改过权重才需要）
```bash
python scripts/_selftest_news.py       # 必须全过
```
汇报时带三样：扫了多少只、事件多少条、需要干预几条。

## 四、输入 / 输出契约

### 输入
| 来源 | 用途 | 缺了怎么办 |
|---|---|---|
| `out/stage3_plan.json` → `positions` | 持仓股名单 | 缺 → 只扫候选 |
| `out/stage1_candidates.csv` | 候选股名单 | 缺 → 只扫持仓 |
| `fuyao.py`（同花顺 iNews） | 新闻/公告/异动/除权 | 接口挂 → 退巨潮公告，仍挂 → 空简报 + 报警 |
| `cninfo.py`（巨潮） | 公告正文与日期 | 同上 |

### 输出
`out/news_events.csv`（一条事件一行，列固定）：
```
layer, code, name, kind, level, tag, date, title, source, url,
r_score, c_score, net_score, tier, mult
```
- `tier`：处置档名（否决 / 降权40 / 降权15 / 加分15 / 加分10 / 不干预）
- `mult`：权重系数（0.00 / 0.60 / 0.85 / 1.15 / 1.10 / 1.00）——**下游只认这一列**
- `url` 与 `date` 缺失的事件**直接丢弃**（不可追溯的新闻等于没有）

`out/news_brief.md`：人读简报，按 level 排序，顶部是第 5 步那三行结论。

**下游怎么用我**：`plan.py` 的 `apply_news()` 读 csv，按 `code` 取最强的 `mult` 乘到权重上，
再写 `research_filter` 供计划书展示。所以 `mult` 写错 = 权重错 = 决策错。

## 五、两套分，方向相反

### R 分（风险，0–100，越高越危险）
```
R = 事件基线(0–60) + 0.5 ×（来源确定性 0–15 + 时效 0–15）
```
**关键性质：没有风险事件时 R 恒为 0。** 来源与时效只放大「已经发生的风险」，
绝不凭空制造风险。（若把五维直接相加，
一条普通公告也能拿 30 分被降权。）

### C 分（催化，0–30，越高越值得加码）
```
C = 事件强度(0–22) + 来源(0–4) + 时效(0–4)
   来源项 = 来源确定性 × 4/15；时效项 = 时效 × 4/15
```

### 处置档（R 优先，利好不能冲抵利空）

| 档位 | 触发 | 权重系数 | 具体动作 |
|---|---|---|---|
| **否决** | `tag ∈ VETO_TAGS` 或 `R ≥ 60` | 0.00 | 候选剔除；持仓处置由 Lead 手工出单（R≥85 建议清仓，须人工确认） |
| **降权40** | `R ≥ 40` | 0.60 | 权重打六折，禁加码 |
| **降权15** | `R ≥ 25` | 0.85 | 权重打八五折，只记录 |
| **加分15** | `C ≥ 22` | 1.15 | 允许在 25% 上限内加码 |
| **加分10** | `C ≥ 15` | 1.10 | 允许小幅加码 |
| 不干预 | 其余 | 1.00 | 只归档 |

`VETO_TAGS = {"立案调查", "退市风险", "会计问题"}` —— 这三个不看总分，直接出局。

## 六、阈值为什么是这些数（成本约束推出来的）

单票上限 = 本金 10%。以 5 万本金为例：单票 5,000 元，一次往返成本约 0.4%
（费用口径与「最低收费追平点」的推导见 `SKILL.md` §1，此处不复述）。**事件要对单票产生 > 0.4% 的影响，动手才不亏。**

校准结果：强正面事件历史超额只有 +1.1% ~ +3.3%，强风险事件 -10% ~ -23%。
- 所以**否决要狠**：-15% 的量级，任何成本都不该扛；
- **加分要轻**：+2% 的量级，加码只该在 1.10–1.15；
- 中间地带（±5% 以内）不值得交易，一律「不干预」。

| 担保 / 资产减值 / 质押冻结 | 5 / 5 / 6 | 两池均无稳定负超额 → 噪音 |
| 解禁 / 再融资 | 6 / 6 | **[先验]** 未取得样本 |
| 回购 | 14 | 优质池 +3.26%，唯一稳定正超额 |
| 分红 | 12 | +3.11% |
| 业绩快报 | 10 | 坏股池 +2.80% |
| 股权激励 | 8 | +1.07% |
| 增持 / 重大合同 / 中标 | 5 / 6 / 5 | 增持 −1.94%，合同 n=2 且为负 → 只给一点点 |

DiD 会把「大家一起跌」减掉，甚至翻正（会计问题、行政处罚就是这样）。
判据用 **原始超额 + 跌超5% 比例 + 误杀率** 三者合看：
- 原始超额显著负 + 跌超5% 高 + 误杀 0% → 真硬雷
- DiD 正但原始超额负 → 说明是池子beta，不能因此不扣分（也不该加权重）

## 八、出问题怎么办

| 症状 | 处理 |
|---|---|
| 同花顺接口 429/超时 | `news.py` 自带限速与重试；连续失败 → 退巨潮公告；仍失败 → 写空简报 + 在简报顶部写「事件面未取到」，**不许假装扫过** |
| `news_events.csv` 是空的 | 先确认是「真没事件」还是「抓取失败」：看 `news_brief.md` 的抓取统计行；失败就重跑 `--days 7` |
| 某条事件 url 缺失 | 该条直接丢弃（不可追溯），并在简报里计数「丢弃 N 条无来源」 |
| 打分明显不合理（硬雷只给 20 分） | **不要手改 csv**——改 `R_EVENT`/`C_EVENT` 表并跑 `_selftest_news.py`；这是唯一正确的修法 |
| 发现「要命的事 R 分却很低」 | 最高优先级：记下来，进下一轮重标定的触发条件 |
| 断网 / 无 key | `--offline` 出空简报，汇报时明说「事件面缺席」 |

## 九、已知局限（必须如实说）

1. **硬雷样本来自 ST 股**。ST 股有 5% 涨跌幅限制、退市预期，量级可能与正常股票不同。
   如果只按「正常股也跌 15%」去理解，可能高估。
2. **样本量小**：业绩预亏 n=2、会计问题 n=2、退市风险 n=3。这三条权重应视为「方向可信、幅度不确定」。
3. **标 [先验] 的 5 个标签完全没校准**（商誉减值、监管措施、解禁、再融资、业绩预增）。
4. **时效衰减是假设**（≤3 天 15 分、≤7 天 12 分…），没有单独验证。
5. **内生性死角**：回购、分红本身是管理层信号，可能与管理层对股价的判断相关；
   事件日附近的价格已部分反映信息，20 日窗口可能不足。
6. **只测了个股 20 日超额**，没测更长持有期，也没测「多个事件叠加」的相互作用。

## 十、什么时候重标定

- 累计事件 ≥ 1,000 条（现在 602 条），或
- 距上次 ≥ 2 个季度，或
- 出现「明明是要命的事，R 分却很低」的案例（打脸优先级最高），或
- 池子结构变了（比如放开创业板/科创板）。

重标定命令：

```bash
python scripts/news_calib.py --n 20            # 优质池
python scripts/news_calib.py --codes "a,b,c"   # 指定池（坏股池用这个）
```

## 十一、一句话

**R 分决定「还能不能持有」，C 分决定「值不值得多买」。两者都不改变资格，只改变权重；
中间地带一律不动手——小资金（5 万本金）的成本结构不允许为 ±2% 的事件付 0.4% 的来回。**
